# 年度累積獎金成熟化修正 — 2026-10-13

## 發現與修正

盤點年度八獎金整合時，發現 API 與 Worker 都先取到期獎金前 500 筆，再逐筆判斷最新生命週期。已成熟或沖銷的資料會占用額度；查詢又沒有固定排序，不能保證後續待成熟資料獲得處理。

修正前隔離 PostgreSQL 案例：501 筆已成熟、600 筆待成熟及 2 筆排除資料；第一輪預期成熟 500 筆，實際僅 282 筆，案例 FAIL。這個數字是本次執行觀察，不是舊查詢每次固定結果。

新增共用 `matureDueBonusAwards`，由 API 和 Worker 使用。查詢先限定到期、存在 PENDING_45D 且尚未出現後續生命週期的獎金，依 pendingUntil、bonusAwardId 排序，再取 500 筆。交易內仍鎖定獎金並核對最新狀態，避免重複追加 EFFECTIVE。不改等待期、獎金公式或歷史獎金金額。

## 驗證範圍

新案例的来源獎金由測試直接建立；這是累積資料的成熟化／可付款整合，**不是註冊、下單、八獎金計算至銀行付款的全年端到端模擬**。

- 501 筆已有 EFFECTIVE 歷史的獎金不再占用成熟化名額。
- 600 筆跨 12 個月份建立的待成熟獎金，API 首輪 500、Worker 次輪 100、第三輪 0。
- 每筆新成熟獎金恰有一筆 EFFECTIVE；已沖銷及未到期各一筆不會成熟或進入可付款。
- 六種 BonusAward 來源：REFERRAL、RETAIL_REFERRAL、EQUALIZATION、BINARY、MATCHING、EPV，逐類核對筆數及金額。測試額每筆 10，為測試用既存獎金，不是制度計算結果。
- 共 1,101 筆可付款、總額 11,010；重複 materialize 新增 0。建立付款批次後原筆數全數 ALLOCATED，再建立批次總額 0，沒有重複分配。
- RPV 與 GLOBAL 使用不同來源表及可付款路徑，不硬塞進這個共用等待期案例。
