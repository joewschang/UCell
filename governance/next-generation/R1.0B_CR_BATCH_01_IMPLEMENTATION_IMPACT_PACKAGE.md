## 3. Current runtime versus approved target

The current schema already provides `ProductReference`, effective `ProductRuleProfile`, versioned `PackageProfileVersion`, immutable package purchase snapshots, Order/OrderLine product snapshots, Paper Receipt evidence, Subscription/MonthlyRecognitionSchedule, `Fulfillment`/Shipment state evidence, PvLedger, Award, Payable/Payout, Outbox and AuditEvent. Binary trees currently store a profile version string and Company profile bindings but no approved profile entity with the required count/policy snapshot. Current fulfillment persistence uses snapshot references rather than normalized source-line allocation or serialized-unit records. Existing payout is authority-rich but does not yet establish the full approved finance export lifecycle. Existing UI icon/badge changes at `34e0869` are presentation-only and are retained.

## 4. Database and migration impact

Forward-only migrations are required for the following logical additions, after each design slice is validated:

1. Bootstrap profile/version and immutable per-tree snapshot; approved profile selection and profile materialization evidence.
2. Versioned Commercial Offering plus offering-product/composition/effective-channel rules only where PackageConfig/ProductRuleProfile cannot carry the approved source/version semantics; OrderLine provenance snapshot references.
3. Repurchase-plan compatibility fields or dedicated forward-safe plan snapshot/schedule fields; never reinterpret historical subscription rows.
4. Fulfillment line allocations, serialized units/lots, ERP handoff/outbox claims and reconciliation/exception evidence.
5. Minimal lineage read/projection source edges, period-orchestration state, payout export/result evidence, Operations/Task/Exception/Timeline projections, and Member messaging records as independently approved slices.

No historical migration may be edited. Append-only audit/economic facts remain immutable. Each migration requires fresh `0→current`, pre-change upgrade, schema preflight, relevant Golden and isolated PostgreSQL evidence. Local and Stage synthetic data may be separately reseeded by an explicit non-Production script; no destructive reseed belongs in a production migration.

## 5. API and OpenAPI impact

New API work must use business-safe identifiers, RBAC/BOLA and evidence envelopes. Expected additive resources are profile read/selection, offering checkout/selection, repurchase plan status, fulfillment allocations/scan, protected lineage reads, period-run status, payout batch/export/result, Operations/Member360/Task/Exception reads, and Member Message Center reads. Public contracts must retain P0 identifier rules: no topology inferred from BallNo and no Member UUID leakage. ## 6. Worker, Outbox and scheduler impact

Reuse the existing Outbox, worker lease and recognition infrastructure. Add idempotent event types for fulfillment handoff/reconciliation, repurchase due recognition, lineage/timeline projection and invariant checks. Period Close is one ordered orchestration authority using SettlementCalendar and leases: K0 → K1 → K2, then Global/Welfare and payable preparation. It never transmits money. External ERP transport is an adapter boundary; its actual EzTooL credential/API remains `EXTERNAL_INTEGRATION_PENDING` and does not block core projections/tests.

## 7. Economic engine impact

No second financial ledger is authorized. Extend edges/read models over Order snapshots, PvLedger, Active evidence, organization history, Carry, Settlement, Awards, destinations, Payables/Payouts, Reservoir B and Return/Recovery/Replay. Preserve theoretical zero and ineligible outcomes. Repurchase recognition must snapshot rule/version/parameter, due dates and deterministic remainder. Company awards retain Reservoir B routing. Historical Explain reads snapshots, never current configuration.

## 10. Paper and LINE impact

## 11. ERP, fulfillment and serial impact

Implement the approved `PBBBSSSS` v1 serial semantics with A–E product mappings, validation states and immutable Shipment binding. Fulfillment may have multiple projections, while a repurchase plan normally has one immediate shipment. The adapter records idempotency key, request/result hashes, external reference and reconciliation state. Do not write unsupported ERP tables or invent EzTooL endpoints.

## 12. Payout and bank-export impact

Reuse UnifiedPayable, Recovery and existing batch/line models. Implement DRAFT → REVIEWED → APPROVED → EXPORTED → PROCESSING → PAID/PARTIALLY_PAID/FAILED through forward-safe compatible state evidence, locked export snapshot/version/hash, manual result reconciliation and retry. Generic controlled export/adapter is executable; bank-specific formatter is `BANK_FORMAT_CONFIGURATION_REQUIRED` until an approved bank format arrives. No automatic bank transfer.

## 13. Operations, Member360, Task and Exception impact

Operations and Member360 are read-oriented joins/projections over existing authorities. Task completion never mutates a domain workflow. Exceptions use OPEN/ACKNOWLEDGED/INVESTIGATING/RESOLVED with safe evidence/trace references. Activity Timeline is rebuildable/idempotent. Invariant Monitor creates evidence/exception/task candidates for broken lineage, Company→Reservoir B mismatch, payout reconciliation, overdue recognition, fulfillment/serial mismatch and critical integration failures.

## 14. Security, RBAC, BOLA and privacy impact

Every new mutation/read requires existing authenticated principal/RBAC authority and BOLA checks. Normal Member channels receive safe business references only. Lineage, Member360, bank export and audit operations are privileged, role-filtered and trace-audited. Bank data is masked and excluded from logs/URLs/audit payloads. New projections retain references/hashes rather than duplicate sensitive payloads.

## 15. Historical replay and reconstruction impact

Return, recovery, replay and correction create append-only linked effects. Rebuildable projections must be deterministic and idempotent; a projection failure cannot mutate authoritative facts.
