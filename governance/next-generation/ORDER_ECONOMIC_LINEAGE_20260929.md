# Order economic evidence checkpoint — 2026-09-29

The privileged order-number read now adds `economicEvidence` without changing the existing fulfillment/payment/return fields. All facts are read in one Repeatable Read transaction. This is a read projection, with no new financial writes or migration.

Attribution follows explicit edges: ORDER PV events → BonusAward.sourceEventId → derived BonusAward.sourceAwardId → BONUS_AWARD PayableEntry. Payables include payout batch status and period, without attributing the entire batch total to the order. Recovery evidence is selected through either a linked award or an order ReturnCase; a recovery matching both edges appears once. A return-linked period award is not pulled into the order's award total: `awardIncluded: false` makes that boundary explicit.

An order-linked Subscription is now followed through its authoritative MonthlyRecognitionSchedule. Each recognition joins only its exact `MONTHLY_RECOGNITION` original RPV ledger event (with the previously accepted `SUBSCRIPTION` source retained for compatibility), RPV generation awards, and the immutable RPV HistoricalReplaySnapshot plus append-only replay postings. The schedule PV pointer, when present, must agree with the selected original; duplicate originals and conflicting source/recipient/rule/amount evidence fail closed. The projection reports recognition-time Active eligibility, theory/payable amounts, rule/snapshot identity and replay deltas from stored evidence; it does not recompute history from current state.

Projection references are deterministic SHA-256 references scoped by record kind. Financial records use a field whitelist; raw UUIDs, recipient identity, calculation JSON, bank references, and payout details are not returned. New collections have deterministic ordering. Source-award traversal has a visited set to avoid repeated records/cycles; the database transaction timeout applies to the full read.

Company destinations are selected only through the BonusAward and RPV award IDs already attributed to the order. `reservoirBDestinations` joins their immutable destination and ordered effects, preserving the original final amount and signed replay adjustments separately. Source references join the existing award references; tree, owner, qualification, destination and effect UUIDs and raw parameter snapshots are excluded. Other orders sharing the same Company recipient are excluded.

`periodContributions` selects REFERRAL_K0, BINARY_K1, MATCHING_K2 and GLOBAL replay snapshots by exact GPV source membership in their sealed `evidence.sources` arrays. A matching timestamp or recipient is insufficient. The shared envelope verifier checks stored hashes and parameter evidence; the projection additionally validates row/envelope identity, source order/event/rule/amount/time, unique source membership and the half-open period interval. Inconsistent selected evidence fails closed. Only this order's original GPV inputs, hashed source/settlement references and period/rule/hash metadata are returned. `SEALED_PERIOD_INPUT_ONLY` means input-cohort membership, not per-order entitlement, current retained volume, settlement payment status, or an allocation of whole-period awards. No current graph or financial recomputation is used.

Each selected period now has a separate `periodContext` marked `WHOLE_PERIOD_NOT_ORDER_ALLOCATION`. It projects sealed recipients' historical eligibility, theory and original entitlement with hashed recipient/award references. Append-only postings join through the exact snapshot and entitlement key, validate the original recipient/amount, and expose signed deltas independently. These whole-period amounts never enter the order's direct awards or payables. No current person/ownership lookup is performed.

`returnReplays` follows only this order's ReturnCase IDs to stored replay runs and their ordered period checkpoints, including later periods without the original GPV. It projects run status/horizon, K factors, original/recomputed Binary and Matching entitlements, and original/recomputed left/right carry. Shared hashed recipient references connect award and carry rows. Raw action keys, identities, impacted-qualification lists and calculation JSON are excluded. Amount fields are parsed as decimals and output is whitelisted. `CALCULATION_CHECKPOINT_NOT_PAYMENT` explicitly applies to both MAX_HORIZON and CONVERGED: a checkpoint or converged status alone does not prove monetary posting, payout or bank payment.

Each run's `recordedEffects` separately follows its stored V1 action/state evidence. The canonical return action must agree with the run; a present immutable ReplayAction must match the return, run, state and completed result. Exact-action Binary/Matching postings are checked against verified snapshots and the checkpoint's original/recomputed recipient amounts. Correction awards, return recoveries and Reservoir B effects are loaded through their explicit IDs/relations and checked against the posting's signed delta and original source. Persisted carry projections join the exact action, state, Binary batch, rule and period and must equal the checkpoint's recomputed recipient carry. Each projected period links back to its checkpoint reference. Different actions in the same batch are excluded. Missing legacy V1 links are `SOURCE_LINK_UNAVAILABLE`; valid links without rows are `NO_RECORDED_EFFECTS`, regardless of run status. `RECORDED_EFFECTS` reports observed rows, not completeness, payable creation, payout or bank payment; `actionCompleted` separately reports matching immutable action evidence. Source ledgers remain unchanged.

`gpvRetention` reports current original GPV less cumulative POSTED ReturnLine GPV reversals through the exact original order-line mapping, using the same subtraction basis as the historical replay engine. It excludes DRAFT/CONFIRMED/VOIDED cases and rejects negative/excess reversals, cross-order line conflicts and ambiguous original-event mapping. Missing line evidence is `SOURCE_LINE_UNAVAILABLE` with null retained/reversed amounts. `CURRENT_POSTED_RETURN_STATE` distinguishes this current read from immutable original or past checkpoint amounts. Each included return line has a hashed reference. No historical amount is overwritten or recalculated into an award.

Positive downstream replay corrections now join only their exact BONUS_AWARD PayableEntry and optional PayoutLine. Recipient and gross amount are checked against the correction. Payout-line/batch references, stored statuses and ordered append-only payment result amounts are whitelisted; bank/payment references, actors, raw IDs and detail JSON are omitted. Payout amounts are explicitly `WHOLE_PAYOUT_LINE_NOT_CORRECTION_ALLOCATION`: one line can combine unrelated payable sources. `CUMULATIVE_LINE_REPORTS_NOT_ADDITIVE` preserves repeated partial/final reports without summing them. An empty payable list or null payout remains explicit; merely recording a correction does not assert payable creation or payment. This is stored external-result evidence, not a bank transfer or independent bank verification.

EPV originals and order-linked RPV recognition originals now expose `RECORDED_PV_AND_ENTITLEMENT_STATE`: original PV plus exact `reversalOfEventId` adjustments and snapshot-linked replay entitlement baselines/deltas. Type, recipient, rule and adjustment-kind conflicts, negative PV balances and inconsistent entitlement delta chains fail closed. EPV can have a positive adjustment after monthly redistribution; it is not capped at original volume. `replayedEntitlements` covers only entitlements with stored replay postings; empty results do not mean zero entitlement. This is persisted state, not a fresh eligibility calculation or proof all accepted returns have been replayed. RPV schedule retained ratio (nullable for legacy data) and POSTED cancellation/refund facts are shown separately and never applied speculatively to historical awards.

Direct/return-linked recoveries and downstream replay recoveries now expose exact RecoveryApplication rows, hashed payout-line references, applied amounts and stored batch status. The payout recipient must match the recovered award recipient and application amounts must be positive. Both views share the same application references. `RECOVERY_OFFSET_NOT_CASH_PAYMENT` distinguishes offset usage from bank payment. Raw payout details and identities are excluded; original recovery amounts, current recovered/outstanding counters and the application list remain separate evidence.

Exact OrderLine sources now also join RETAIL_REFERRAL awards, including zero payable rows, without admitting other award kinds through line IDs. Original Active and K fields and safe line references are exposed. The first structured Admin read view and eight-family source-edge audit are documented in [coverage and UI evidence](ECONOMIC_LINEAGE_COVERAGE_UI_20260929.md).
