## Implemented behavior

The model chooses one allowlisted read intent; it receives the redacted question and no operational result rows. Application SQL produces answers, money, periods and CSV. Member reads are bound to the authenticated person and current personal qualification history. Company principals, company-origin qualifications and active system pool entries are excluded. A transfer, session revocation, capability expiry or account lock prevents subsequent reads and downloads.

Company reporting covers confirmed gross payment receipts and payment-confirmed order counts. It does not label these amounts as net revenue or GPV. Fee/product splits are shown only when every included order has the verified new qualification policy snapshot. Partial payments, duplicate confirmations and mixed currencies fail closed. Coupon reports use fixed joins when the source tables exist. No arbitrary SQL, writes, other-person lookups, forecasts or comparisons are supported.

Member queries cover current qualifications, own purchaser orders, active-status/performance evidence and bonus finality. Missing financial evidence is unavailable, not zero. Order lists and bonus lists are capped at 20, with truncation notices. Transfer-boundary history is not returned. Existing recognition code is reused; the model does not calculate GPV.

Conversations, turns, immutable result snapshots, report jobs, feedback and audit metadata persist in PostgreSQL. Turns use idempotency and serialized quota reservation. Cancellation prevents result publication; interrupted work is failed rather than silently replayed. The UI deliberately submits independent questions without free-form conversational memory. Small CSV reports are generated from a ready snapshot, not a second financial query. Snapshot/download expiry is 24 hours; answer payloads expire after 30 days and audit metadata after 180 days. Original questions are not stored; SHA-256 hashes and execution metadata are retained.

Knowledge has immutable versions, effective dates, draft → review → publication, separate author/approver checks, optimistic revisions and overlap rejection. Nine proposed answers were created as `IN_REVIEW` by a clearly identified automated release author. None were falsely marked human-approved. Until reviewed and published, FAQ responses correctly say no approved source is available. Reviewable content is in `ai-stage-knowledge.json`.

## Model and limits

Azure resource `ucell-stage-ai-20261022`, resource group `rg-ucell-stage`, region `eastus2`; deployment `ucell-stage-planner`, model `gpt-4.1-mini`, version `2025-04-14`, Standard capacity 10. The key is held in a Container App secret reference, never frontend code.

The application reserves 8,192 tokens per attempt against a 500,000-token monthly Stage ceiling. Reservations are conservative and not refunded on failure, so the initial configuration permits at most 61 attempts per month, shared by all testers. This is an application admission ceiling, not a dollar-denominated Azure billing cap. Direct provisioning/model verification calls are separate from this counter. Members have 5 requests/minute and 50/day; admins 10/minute and 200/day. The model response limit is 300 tokens and the query execution deadline is 24 seconds. Monthly periods use Asia/Taipei; a current-month end is capped to the actual query time.

Function-call choices and disabled parallel calls follow the [official OpenAI function-calling documentation](https://developers.openai.com/api/docs/guides/function-calling). Server-side validation remains authoritative.
