# Offline Dot uploader preparation

This is local engineering preparation only. A Node HTTPS adapter and local SQLite retry journal are now implemented, but there is no token acquisition, secret, new principal, deployment, production request, schedule, or SwaggerHub update. `uploader.mjs` has no CLI and performs no I/O at import. Both `tokenProvider` and `transport` must be explicitly supplied. The production route remains disabled pending separate activation evidence.

## Request and transport contract

1. Generate an unbranded background and prepare exactly `{date,title,message,contentBase64}` plus a caller-generated UUID using `prepareRequest`. Persist the resulting `{idempotencyKey,body}` together in approved durable storage **before** transmission. Use the explicit local SQLite journal described in [JOURNAL.md](JOURNAL.md); genuinely persistent cross-schedule storage is not yet configured. Do not persist bearer tokens. A restart must reload the exact pair, never create a replacement image/key to overcome a conflict.
2. Configure the exact HTTPS DNS endpoint ending in `/api/v1/integrations/dot/daily-greetings/publish`; port 443 only, no credentials/query/fragment. There is no default endpoint. The configured hostname must later be approved by network policy; local syntax validation cannot prove DNS ownership or permissions.
3. Supply `tokenProvider({signal})` returning a fresh opaque bearer string for each attempt. It must not log or persist credentials or tokens. This uploader does not parse tokens or cache them; it drops its reference after transmission. JavaScript strings cannot be guaranteed physically zeroed from process memory. Debuggers, crash dumps and external adapters are outside this module's controls.
4. Supply `transport(url, options)` returning a Web `Response`. It MUST respect the exact destination, `redirect:'error'`, AbortSignal, TLS verification and the environment proxy. It must never forward authorization to a redirect or log headers, bodies, or raw upstream exceptions. Use `createHttpsTransport` in `https-adapter.mjs`: it uses Node HTTPS with certificate verification, TLS >=1.2, an environment-proxy agent, an 8 KiB response-header limit, 4096-byte response limit, and a total 30-second timeout that destroys the request/socket. It never follows redirects. Low-level request/stream mocks verify this implementation; real TLS/proxy/HTTP integration is NOT verified. The uploader also bounds provider/transport waits even if they ignore cancellation; the real adapter honors the AbortSignal. Injected adapters and runtime diagnostics still need review.
5. `upload(prepared)` accepts only validated JSON, the eligible Taipei date (07:00 boundary, earliest 2026-11-17), plain short text, and bounded PNG. Validation repeats before retries and after acquiring a token, preventing a date-boundary race. It snapshots the body/key and reuses identical bytes on every retry. Transport failures and HTTP 429/502/503/504 get at most 3 attempts with 1s/2s waits in standalone mode. Journal mode forces one attempt per invocation and enforces a durable total cap of 3, including interrupted attempts; do not wrap it in a fresh standalone retry loop. Other statuses, including 401/403/409 and redirects, stop immediately. No automatic credential broadening, key replacement, date replacement or deletion occurs.
6. Successful HTTP 200 must return bounded JSON with matching date, UUID id, and `PUBLISHED` or `ALREADY_PUBLISHED`. Only these three fields are returned. Invalid or uncertain responses never authorize a different payload/key. Inspect state or retry the same stored request after an uncertain outcome; after the date rolls over, stop and reconcile because this endpoint rejects old dates. The module logs nothing and exposes only fixed error codes, never upstream response bodies.

The PNG validator accepts a deliberately strict subset: 1024×1024 noninterlaced 8-bit RGB/RGBA, PNG signature, IHDR/contiguous IDAT/IEND only, valid CRC, bounded exact decompressed scanline size, valid filter bytes, and no trailing data. Maximum encoded PNG size is 8,000,000 bytes. Metadata, palette and animation chunks are rejected. A future approved image preparation step may need to normalize generated PNGs to this subset. This is structural validation; it does not prove that an image is unbranded or licensed. Server native decode, canonical hashing, trusted logo/QR composition and published-date protection remain authoritative and unchanged.

## Token acceptance policy

`cloud-greeting-auth.ts` retains jose RS256 signature/issuer/audience verification and pinned tenant/client/object ID, app-only identity, no scopes, sole route-specific role. It now uses zero clock tolerance and additionally requires safe integer times, `iat >= 0`, `iat <= now < min(exp, iat + 3600)`, and `0 < exp - iat <= 5400`. This accepts normal 60–90 minute Entra tokens for strictly less than one hour from issuance; it never accepts an expired token or adds a five-second extension. Exactly age 3600 is rejected. The optional generate route shares this stricter effective-age check. No tenant lifetime policy is changed.

Reference: [Microsoft access-token lifetime](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens#token-lifetime). Long-lived/CAE tokens exceeding 90 minutes fail closed; do not loosen the bound without reviewing actual dedicated-principal claims.

## Network-secret hypothesis: NOT live validation

[Cloud environments documentation](https://learn.chatgpt.com/docs/environments/cloud-environments) describes network-secret placeholders substituted by the HTTPS proxy on port 443 for allowed domains. A future client-credentials adapter might use this for `login.microsoftonline.com`, an approved dedicated principal, and an explicitly pinned API audience with `.default` scope. It must use the environment proxy and never print the returned bearer.

**The actual substitution of a placeholder after application/x-www-form-urlencoded encoding has NOT been tested.** `encodeClientCredentials` only serializes a candidate request; it does not read environment values or send anything. A fixed fake sentinel test proves form-encoding roundtrip only. No form is sent by these modules. Mock provider success does not establish substitution, correct escaping, identity custody, live token issuance, actual tenant claims, network reachability, proxy/TLS behavior, or PC-off operation. Do not pass a real secret via direct environment variables, command arguments, files, logs or chat to work around an unverified placeholder path. No network policy changes are part of this work.

Before activation, separately verify supported secure custody; approved dedicated principal/role and actual pinned IDs; form encoding and proxy substitution in a safe authorized test; real signed claims and first-hour refresh behavior; live verification of the implemented redirect-blocking bounded HTTP adapter; approved durable storage and retention for the local journal; and staged end-to-end publication/retry/public retrieval/QR/PC-off checks. Follow existing release/backup/restore gates and reconcile production overlays. Keep paid Azure image generation off and the November 16 publication untouched.
