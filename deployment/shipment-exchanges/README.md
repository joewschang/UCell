# 出貨單退換貨

## 使用方式

在後台「出貨與序號核對」載入原訂單。已有物流收件、配送中或送達紀錄的物流單會提供「退換貨」入口。

### 同品換貨

1. 勾選要退回的商品序號並填寫換貨原因。每次可以選擇部分商品，最多 100 件。
2. 建立申請後，在原出貨單下方查看換貨紀錄。
3. 收到實物時逐件核對序號，再勾選本次收到的商品驗收。可以分批驗收。
4. 全部驗收完成後，按「建立同品補寄出貨單」。系統為這一件換貨案件建立一次補寄配置。
5. 進入補寄出貨單，依現有流程掃描合格的新商品序號、裝箱、確認配送資料並登錄物流。建立補寄單本身不代表已寄出。

尚未驗收任何商品時可取消申請；取消紀錄保留，原商品可重新申請。已有驗收紀錄的案件不能直接取消。

| 案件狀態 | 操作意義 |
| --- | --- |
| 待收回商品 | 已建立申請；可能尚未收到或僅收到部分商品。 |
| 已收齊，待建立補寄單 | 所選商品皆已驗收，可建立補寄配置。 |
| 已建立補寄單 | 可追蹤對應的新出貨單；實際物流進度仍以該出貨單為準。 |
| 已取消 | 保留原因、序號與歷史，不再提供補寄額度。 |

### 退貨退款或更換其他商品

按「帶入原訂單辦理退貨」，系統依精確訂單號讀取原單並核對，沿用既有退貨數量、金額與業績回沖規則。財務退貨入帳與實際退款付款是不同作業，不能將入帳畫面當作退款已完成。

跨商品或有價差的需求使用既有退貨及重新下單流程。本次同品換貨不提供跨 SKU 替換、自動差額收付或修改原商品價格。

## 資料與操作限制

- 原訂單、原出貨配置、原序號綁定與原經濟用途快照完整保留。
- 同品補寄延續原訂單權利，不建立第二筆銷售、不新增或回沖業績與獎金事件。
- 退回序號保留為 `RETURNED`，不能直接當成合格新商品再次配置。
- 同一原序號只能被一個有效換貨案件占用；重試與重複點擊不產生雙份案件或補寄單。
- 財務退貨待驗收與尚未完成補寄的換貨設交叉檢查，避免同一商品同時取得退貨與補寄權利。
- 同品補寄額度只屬於對應已驗收換貨案件，不能借給一般出貨使用。
- 倉務及系統管理員可操作；稽核角色可查看紀錄。

## 發布與回復

本次包含後台、API 及新增資料表的 migration。依 `deployment/PRODUCTION.md` 發布：先在臨時 PostgreSQL 驗證 migration 與受影響測試，完成資料庫新增 migration 後才發布依賴新資料表的 API，最後發布後台。

回復舊 API／後台映像時保留換貨資料表與案件證據，不執行資料表刪除。若已存在新補寄配置，回復前需確認舊版本的出貨配置上限處理；不能把補寄單偽裝成原出貨配置或刪除原證據。

OpenAPI 僅在原始碼內產生與檢查，依既有暫停決定不主動發布 SwaggerHub。正式站更新須保留實際 migration、映像 digest、revision 與驗證證據。
